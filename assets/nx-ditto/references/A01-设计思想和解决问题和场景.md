# A01 · 设计思想、解决什么问题、适合什么场景

## 解决什么问题

Windows 剪贴板只有一个槽位。复制新内容就覆盖旧内容，几分钟前的代码片段、
刚截的图、刚复制的路径全部消失。找回它们只有两个办法：

1. **翻历史记录**（Ditto 这类剪贴板管理器）：后台常驻监听，每次复制落库
2. **自己再截一次 / 再复制一次**

nx-ditto 不做第 1 件事——**Ditto 已经在做了**。它做的是第 3 件事：
把 Ditto 落下来的库变成**可查询、可导出、可被 agent 消费**的数据。

```
Ditto（后台采集）  →  Ditto.db（SQLite）  →  nx-ditto（查询 / 导出 / 面板）
```

## 适合什么场景

- 「刚才复制的那段报错日志 / 那条命令 / 那个文件路径是什么？」
- 「把最近复制过的几张截图导出来看看」——Ditto 存的是原始位图，需要还原成 PNG
- 给 agent 用：剪贴板历史是高频、低价值但**经常正好需要**的数据，
  一条 `clip list --json` 就能拿到，不该靠人肉复述

## 不适合什么场景

- **跨设备剪贴板同步**：这是 Ditto / 剪贴板同步工具的活，本工具只看本机库
- **敏感信息**：剪贴板历史里可能有密码、token、验证码。用之前想清楚，
  本工具会把内容原样打出来
- **没有 Ditto 的机器**：本工具依赖 Ditto 的库；Ditto 没装过就没有数据可读
  （工具会明确报错，不会假装是空的）

## 设计思想（只讲影响用法的部分）

**1. 只读别人的库，不接管采集。**
Windows 剪贴板的历史必须靠一个常驻进程监听（`AddClipboardFormatListener`）
才能积累。Ditto 已经在干了，nx-ditto 不再养一个自己的监听器——
省一个常驻进程，也省一份重复实现。

**2. 「当前」和「历史」是两件事，命令上分开。**
`clip now` 读的是此刻剪贴板里的值（任何时刻都能用，不需要任何历史）；
`clip list` 读的是 Ditto 攒下来的历史（需要 Ditto 跑过）。
混在一起会让人以为「没历史 = 没数据」。

**3. 原始位图要还原，不能只存字节。**
Ditto 存的是 CF_DIB（`BITMAPINFOHEADER` + 像素），不是 PNG。
同一台机器上 `BI_RGB` 与 `BI_BITFIELDS` 两种压缩方式混着出现，
像素区起点差 12 字节——写死偏移会解出花屏。工具按实际长度反推像素区，
再自己编码 PNG。

**4. CLI 与面板同源。**
一条命令同时声明 CLI 路径与 HTTP 路由，命令表、路由表、帮助文本全部由它派生。
面板上有的操作，CLI 一定有等价命令——不是靠人记，是结构上不可能分叉。

**5. 只写新文件。**
导出图片时不覆盖同名文件（自动加 `-1` 后缀），并提供 `--dry-run`
先看「将要写什么」。导出是对用户文件系统的写操作，值得多一层保险。

## 数据从哪来、边界在哪

- 库路径查找顺序：`NX_DITTO_DB` 环境变量 → `%APPDATA%\Ditto\Ditto.db`
  → Ditto.exe 同目录（便携版）
- 库结构：`Main` 存条目元信息，`Data` 存每条目的各格式内容
  （`CF_UNICODETEXT` 文本、`CF_DIB` 位图、`CF_HDROP` 文件列表、`HTML Format`）
- 顶层条目是 `bIsGroup = 0 且 lParentID = -1`；被拖进 Ditto 分组的条目默认不列出，
  加 `--include-grouped` 才算进来
- 库是 Ditto 写的，nx-ditto **只读**，不会改动 Ditto 的任何数据
